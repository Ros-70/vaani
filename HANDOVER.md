# Handover

Written at the end of the first autonomous build session. Assume the next
session has no memory of this one beyond the repo contents and this file.

## Status in one paragraph

A complete Kotlin/Jetpack-Compose Android project exists: the IME service,
its Compose keyboard surface (letters/symbols/more layers, tap/hold race,
long-press diacritics, dictation panel, edit row, suggestion strip), a Room
+ DataStore data layer, all seven companion-app screens, a whisper.cpp JNI
integration, and a unit + instrumented test suite — **and as of this
session's last push, CI is fully green**: unit tests, lint, the real
`assembleDebug` build (whisper.cpp fetched and compiled from source for
real, for three ABIs), and the instrumented test actually driving Vaani's
real on-screen keys against a real `EditText` on a real emulator, through
a real `InputConnection`, and asserting the committed text — all passing.
Getting there surfaced and fixed several genuine bugs, not just CI-script
issues; see "Real bugs found and fixed" below before assuming anything
not listed there is solid.

## Real bugs found and fixed (not just CI-script issues)

Getting CI green took about a dozen iterations. Most were CI-script
mistakes (wrong component-id format in the workflow, a multi-line shell
loop that `android-emulator-runner` silently splits into separate
invocations per line, an artifact-upload quota that shouldn't fail the
build, installing the app before trying to enable it as a keyboard). Two
were genuine application bugs worth knowing about specifically:

1. **`EnableVaaniState.inputMethodId()` built the wrong id entirely.**
   Android identifies an IME by `ComponentName.flattenToShortString()`,
   which *abbreviates* a class name that starts with its own package name —
   `com.vaani.keyboard.ime.VaaniInputMethodService` under package
   `com.vaani.keyboard` becomes `com.vaani.keyboard/.ime.VaaniInputMethodService`,
   confirmed against a real device's own `adb shell ime list -a` output.
   The code was hand-concatenating the *fully-qualified* class name, which
   never matches either `getEnabledInputMethodList()`'s ids or
   `Settings.Secure.DEFAULT_INPUT_METHOD`'s value — meaning the "is Vaani
   enabled / is it selected" detection that HARD REQUIREMENT #4 depends on
   was silently broken from the very first commit, not just in CI. Fixed
   with `ComponentName(...).flattenToShortString()` instead of string
   concatenation; `EnableVaaniStateTest` now asserts the exact expected id
   so this can't regress silently again.
2. **The real IME process crashed** the first time the instrumented test
   actually got far enough to show it:
   `IllegalStateException: ViewTreeLifecycleOwner not found from
   android.widget.LinearLayout{... android:id/parentPanel}`.
   `InputMethodService.setInputView()` wraps whatever
   `onCreateInputView()` returns inside its own internal decor hierarchy (a
   `LinearLayout` with id `android:id/parentPanel`, above the `ComposeView`).
   Compose's default window-level recomposer resolves a
   `ViewTreeLifecycleOwner` starting from that window's *absolute root*
   view — the system's own wrapper, not our `ComposeView` — and
   `InputMethodService` exposes no supported way to reach that real root to
   tag it ourselves. Fixed by hosting Vaani's own `Recomposer`
   (`AndroidUiDispatcher.CurrentThread` + `runRecomposeAndApplyChanges()`,
   the standard pattern for Compose hosts outside Activity/Dialog) and
   handing it to the `ComposeView` via `setParentCompositionContext()`,
   which skips the window-recomposer lookup entirely. **If you ever see
   this exact crash again** (e.g. after a Compose version bump changes
   this internal), that's where to look first.

Both are the kind of thing that would have shipped broken and only shown
up the first time a real person tried to turn Vaani on — exactly what
actually exercising this against a real system, not just compiling it,
is for.

## What's left

- **Walk the full acceptance checklist on a real phone.** CI proves the
  keyboard can be turned on, typed on, and built — it does not prove
  dictation produces a correct transcription, that the keyboard looks
  right, that long-press/backspace-repeat/space-drag feel right, or that
  it behaves inside WhatsApp/Gmail/Notes specifically rather than a bare
  `EditText`. This is the single most important thing left, and the first
  time anyone should trust this beyond "it builds and the simplest
  possible typing case works."
- **whisper.cpp's actual transcription accuracy is unverified.**
  `jni_bridge.cpp` compiles and links against the real API now, but no
  model file or real audio has been run through it. If dictation produces
  garbage or crashes, start by checking `whisper_full_params`' field names
  and `whisper_init_from_file_with_params`'s signature against whatever
  whisper.cpp version `v1.7.2` actually pins — those were written from
  memory/documentation, not from reading the vendored header.
- **The TRANSLIT dictionary is intentionally scope-limited** (per the build
  brief): the same small 16-word Latin→Devanagari lookup from the
  prototype, nowhere near enough for daily use. A real transliteration
  engine or library is a known, flagged stretch goal — not a blocker.
- **Streaming transcription** re-decodes the whole growing buffer on each
  chunk rather than true incremental decoding (DECISIONS.md #4) — correct,
  gets slower as an utterance grows long. Worth revisiting once dictation
  accuracy itself is confirmed.
- **IndicWhisper** (the fourth model in the Models list) is a community
  model not bundled with whisper.cpp — R will need to find/convert it
  separately, same as the build brief describes.
- Exact dependency versions (Compose BOM 2024.09.00, Room 2.6.1,
  Navigation Compose 2.7.7, etc.) have now resolved successfully in CI
  multiple times — no longer a concern.

## Everything else worth knowing

- `DECISIONS.md` has the judgment calls made along the way, each with the
  reasoning — read it before second-guessing something that looks
  arbitrary (per-model Import buttons, the popup hit-testing approach, the
  DataStore/Room split, etc.).
- No `BLOCKERS.md` was needed — nothing here required a paid service, a
  secret/API key, a destructive git operation, or publishing anywhere.
- The sandbox this was built in had no Android SDK/NDK pre-installed and a
  network policy allowing only `dl.google.com`/`dl-ssl.google.com` plus
  package managers (no generic internet). A minimal Android SDK was set up
  from scratch there (command-line tools + platform 34 + build-tools) to
  compile-check as much as possible before ever pushing, which is how
  several Compose/Kotlin mistakes were caught before CI saw them at all —
  but running the actual test suite, the native build, and the emulator
  were only ever possible in CI itself, which is why getting CI green took
  the iteration described above rather than happening on the first push.
